# Structure and Format

> **Owner:** Platform Engineering lead · **Last verified:** 2026-11-25 · **Status:** Draft
> **Sources:** Conventional Commits 1.0.0 (conventionalcommits.org); docs.astral.sh (Ruff formatter); mypy documentation (`--strict`); MADR 4.0.0 (MADR project documentation); docs.gitlab.com (Code Owners)

## Purpose
Define what a repository looks like, how code is laid out inside `src/`, how things are named and formatted, how documents and ADRs are written, how commits are worded and who owns which paths. The layout is generated by the Copier template (future work); until then copy it from this doc. Layering rationale and the architecture fitness tests belong to [03-architecture.md](./03-architecture.md); this doc owns the tree and the dependency rules in table form. Tool versions and configuration files are in [00-tech-stack.md](./00-tech-stack.md).

## Rules

### Repository layout
- **STR-001** [MUST] [review] Every service repo MUST follow the reference layout below. A new top-level directory or a missing standard one MUST be justified in an ADR.
- **STR-002** [MUST] [lint: ruff] Code MUST use the `src/` layout: one importable package at `src/<package>/`, tests outside it under `tests/`.
- **STR-003** [MUST] [review] Generated or build output (`dist/`, `build/`, caches, SBOMs, eval results) MUST NOT be committed. Ignore rules are in [07-ignore-files.md](./07-ignore-files.md).
- **STR-004** [MUST] [review] `README.md` MUST state purpose, owning team, `make install` and `make run`, link to the OpenAPI file (if any) and the runbook.
- **STR-005** [MUST] [review] No empty or placeholder directories, dead modules or commented-out files MUST be left in the tree.

### Source tree and dependency rules
- **STR-006** [MUST] [review] Code inside `src/<package>/` MUST follow the canonical source tree below. New modules go into an existing layer; a new layer requires an ADR and an update to this doc.
- **STR-007** [MUST] [test: import-linter] The dependency rules above and the layer map in [03-architecture.md](./03-architecture.md) MUST be enforced by import-linter contracts that run in `make check`. A violation fails the build; it is not waived by a comment.
- **STR-008** [MUST] [test: import-linter] `domain/` MUST NOT import from any other layer, any framework, any I/O library or any LLM SDK. It holds pure business logic.
- **STR-009** [MUST] [test: import-linter] `api/` MUST contain transport code only (routers, request and response schemas, error mapping, middleware) and call `application/` use cases. Business rules in routers MUST NOT exist.
- **STR-010** [MUST] [test: import-linter] All outbound I/O (database, HTTP clients, queues, storage, Key Vault, LLM) MUST live in `adapters/` and implement `Protocol`s declared in `application/ports.py`.
- **STR-011** [MUST] [test: import-linter] `ai/tools/` MUST call `application/` use cases and MUST NOT import `adapters/` directly. `ai/agents/` MAY use `ai/tools/` and `adapters/llm/` and MUST NOT import `api/`.
- **STR-012** [MUST] [test: architecture] `main.py` MUST be the only composition root (wires adapters into use cases), and `config.py` the only module that reads the environment (see [06-secrets-and-env.md](./06-secrets-and-env.md)).
- **STR-013** [MUST] [review] `common/` MUST stay small (generic helpers only) and MUST NOT contain business logic. If it grows past a handful of modules, move code into the layer that owns it.
- **STR-014** [MUST] [review] Each `ai/tools/` module MUST implement exactly one manifest in `registry/tools/`, and each agent directory one manifest in `registry/agents/`. The registry rules are in [25-ai-tool-and-agent-registry.md](./25-ai-tool-and-agent-registry.md).
- **STR-015** [MUST] [review] Prompts MUST live as versioned files under `prompts/`, loaded through `ai/prompts/loader.py`; prompt text MUST NOT be embedded in Python modules.

### Naming
- **STR-016** [MUST] [lint: ruff N] Python names MUST follow PEP 8: `snake_case` modules, packages, functions and variables; `PascalCase` classes; `UPPER_SNAKE_CASE` constants.
- **STR-017** [MUST] [review] Documentation files, ADRs, registry IDs and Terraform directories MUST use lowercase `kebab-case`; ADRs are numbered `NNNN-short-title.md`.
- **STR-018** [MUST] [review] Tests MUST mirror the source tree (`tests/unit/<layer>/test_<module>.py`) and be named `test_<behavior>`; detailed test standards are in [24-testing-standards.md](./24-testing-standards.md).
- **STR-019** [SHOULD] [review] Names SHOULD describe domain concepts, not technology (`ClaimRepository`, not `SqlHelper`), and SHOULD NOT use `utils`, `helpers`, `manager` or `misc`.

### Format and types
- **STR-020** [MUST] [lint: ruff format] All Python MUST be formatted with `ruff format`; `make fmt-check` MUST pass. Style arguments MUST NOT be raised in MRs: the formatter decides.
- **STR-021** [MUST] [lint: ruff] Line length MUST be 100. Do not enable lint rules that conflict with the formatter (Ruff documents W191 and COM812 as conflicting); E501 may still fire because the formatter wraps on a best-effort basis.
- **STR-022** [MUST] [lint: mypy] `mypy --strict` MUST pass on `src/`, `tests/` and `evals/`. All functions MUST be fully annotated, `Any` MUST NOT appear in `domain/`, and each `# type: ignore[code]` MUST have a reason comment.
- **STR-023** [SHOULD] [lint: ruff] Imports SHOULD be absolute and sorted by Ruff's `I` rules; relative imports SHOULD be avoided.

### Documentation format
- **STR-024** [MUST] [review] Repo docs MUST be Markdown: one H1, ATX headings (`#`), sentence-case headings, `-` bullets, fenced code blocks with a language tag, relative links, tables for comparisons. Lines are not hard-wrapped.
- **STR-025** [MUST] [review] Each architectural decision MUST be an ADR in `docs/adr/NNNN-title.md` using the MADR 4.0.0 headings below. ADRs are append-only: a changed decision gets a new ADR that supersedes the old one.
- **STR-026** [MUST] [review] A claim about a tool, version or date in a doc MUST name its source or carry a `VERIFY:` marker.

### Commits and branches
- **STR-027** [MUST] [ci: scripts/check_commit_msg.py] Commit subjects MUST follow Conventional Commits 1.0.0: `<type>[optional scope][!]: <description>`, with type one of `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `revert` and a subject of at most 72 characters.
- **STR-028** [MUST] [ci: scripts/check_commit_msg.py] The MR title MUST also be a Conventional Commit subject, because squash-merge uses it as the commit message. VERIFY: configure the squash commit message template in GitLab project settings and confirm it uses the MR title.
- **STR-029** [MUST] [review] Breaking changes MUST use `!` before the colon and a `BREAKING CHANGE:` footer describing the change and migration.
- **STR-030** [MUST] [review] A commit or MR MUST contain one logical change. Mechanical changes (formatting, renames, dependency bumps) MUST be separate from behavior changes.
- **STR-031** [SHOULD] [review] The scope SHOULD be the layer or area touched (`api`, `domain`, `adapters`, `ai`, `infra`, `registry`, `prompts`, `evals`, `docs`).
- **STR-032** [SHOULD] [review] ASSUMPTION: agent-authored commits SHOULD carry a trailer naming the tool that wrote them. The exact trailer format is an org decision (F5); do not invent a different one per repo.
- **STR-033** [MUST] [review] Branches MUST be short-lived and named `<type>/<ticket>-<short-slug>`. Trunk-based flow details are in [01-codebase-practices.md](./01-codebase-practices.md).

### Code ownership
- **STR-034** [MUST] [review] Every repo MUST contain a `CODEOWNERS` file at the repository root with a default `*` entry and sections for the security-sensitive paths listed below. Owners MUST be groups, not individuals.
- **STR-035** [MUST] [review] The default branch MUST be protected with code owner approval required for matching paths. VERIFY: code owner approval enforcement is a Premium or Ultimate feature per docs.gitlab.com; confirm the tier and fallback with the platform team (F4).
- **STR-036** [MUST] [review] Changes to `CODEOWNERS`, `.gitlab-ci.yml`, `.claude/`, `.mcp.json`, `registry/`, `prompts/` and `infra/` MUST require approval from the owning group, never only the author's own group.
- **STR-037** [MUST] [review] Agents MUST NOT edit `CODEOWNERS` and MUST NOT approve their own MRs.

## Reference repository layout

This is the canonical layout, with two deliberate points: `AGENTS.md` is resolved to an import (see [08-claude-md.md](./08-claude-md.md)), and `.claude/hooks/` is added for hook scripts.

```
<service>/
├── CLAUDE.md                  # agent entry point, short, links to rules
├── AGENTS.md                  # optional; CLAUDE.md imports it with @AGENTS.md (one source of truth)
├── README.md
├── Makefile
├── pyproject.toml             # deps, ruff, mypy, pytest, coverage config
├── uv.lock                    # (if uv adopted)
├── Dockerfile
├── .dockerignore
├── .gitignore
├── .env.example               # committed; real .env never committed
├── .pre-commit-config.yaml
├── .gitlab-ci.yml             # GitLab CI/CD (confirmed)
├── CODEOWNERS
├── .mcp.json                  # approved MCP servers only (project scope)
├── .claude/
│   ├── settings.json          # shared permissions (deny-by-default), hooks, env
│   ├── settings.local.json    # personal, GITIGNORED
│   ├── rules/                 # topic rules, some path-scoped via `paths:` frontmatter
│   │   ├── python-style.md
│   │   ├── testing.md         # paths: tests/**
│   │   ├── security.md
│   │   ├── llm-and-agents.md  # paths: src/**/agents/**
│   │   ├── api-contracts.md
│   │   └── infra-terraform.md # paths: infra/**
│   ├── skills/                # repeatable workflows, e.g. new-endpoint, add-eval, write-adr
│   │   └── <name>/SKILL.md
│   ├── agents/                # subagents, e.g. test-writer, security-reviewer, code-reviewer
│   ├── hooks/                 # scripts referenced from settings.json hooks
│   └── commands/              # optional slash commands (skills now cover most uses)
├── src/<package>/             # src layout; canonical tree in "Source code tree" below
├── tests/                     # unit/ mirrors src/; plus integration/ contract/ e2e/
│   ├── unit/  integration/  contract/  e2e/  conftest.py
├── registry/                  # AI tool and agent manifests (see 25)
│   ├── schemas/  tools/  agents/
├── evals/
│   ├── datasets/  (synthetic only)  evaluators/  thresholds.yaml
├── prompts/                   # versioned prompts as files, reviewed like code
├── docs/
│   ├── adr/  use-cases/  runbooks/  api/openapi.yaml
├── infra/                     # Terraform modules and env configs
└── scripts/                   # check_commit_msg.py, registry_check.py, check_ignore.sh
```

Notes:
- `tests/`, `evals/`, `registry/`, `prompts/`, `docs/`, `infra/` and `scripts/` are top level because each has a different owner, reviewer or CI job.
- `docs/` as a folder is a repo convention, not a Claude Code feature.
- `.claude/hooks/` holds scripts referenced from `.claude/settings.json`; see [08-claude-md.md](./08-claude-md.md).

## Canonical source tree

```
src/<package>/
├── __init__.py
├── main.py                    # app entry (composition root only; wires deps)
├── config.py                  # pydantic-settings, the only place env is read
├── observability.py           # OTel + structlog setup (single init)
├── api/                       # transport layer (HTTP); no business logic
│   ├── routers/  schemas/  deps.py  errors.py  middleware.py
├── domain/                    # pure business logic; NO I/O, NO framework, NO LLM imports
│   ├── models/  rules/  services/  errors.py
├── application/               # use cases / orchestration of domain + ports
│   ├── use_cases/  workflows/  ports.py   # ports = Protocols the adapters implement
├── adapters/                  # all I/O lives here (outbound)
│   ├── db/  http_clients/  queue/  storage/  keyvault/
│   └── llm/                   # Foundry client wrapper: retries, timeouts, redaction, telemetry, structured output validation
├── ai/                        # AI-specific code, isolated from domain
│   ├── agents/                # one dir per agent: agent.py, manifest ref, state, policies
│   ├── tools/                 # one module per tool; implements its manifest in registry/tools/
│   ├── prompts/loader.py      # loads versioned prompts from /prompts, verifies hash
│   ├── retrieval/             # RAG: index, retriever, access-control filter
│   ├── guardrails/            # input/output validation, PII redaction, injection checks
│   └── evals_hooks.py         # runtime sampling for online eval
├── security/                  # authn/authz, identity, permissions helpers
└── common/                    # tiny shared utilities (no business logic; keep small)
```

Companion directories:

```
registry/
├── schemas/tool.schema.json  agent.schema.json
├── tools/<tool-id>.json
└── agents/<agent-id>.json
docs/
├── adr/NNNN-title.md          # MADR-style; uses use-case catalog prompts
├── use-cases/<case>.md        # filled-in catalog template per real use case
└── runbooks/
```

### Dependency rules

Direction of imports, as a single statement (the contracts are written from it):

- `api -> application -> domain`; `adapters -> application ports`; `domain` imports nothing outward.
- `ai/tools` may call `application` use cases and never adapters directly.
- `ai/agents` may use `ai/tools` and `adapters/llm`, never `api`.
- `config.py` and `main.py` are the only environment reader and the only composition root.

The row-by-row layer map (what each layer may and must not import, including `security/`, `common/`, `ai/retrieval/` and `ai/guardrails/`) and the import-linter contract syntax are owned by [03-architecture.md](./03-architecture.md). This doc does not repeat the table, so there is one place to change it.

## Format and style

### Ruff and mypy
Configuration lives in `pyproject.toml` (see the skeleton in [00-tech-stack.md](./00-tech-stack.md)). Ruff's formatter is a near drop-in replacement for Black's stable style; line length is 100 and `docstring-code-format = true`. mypy strict is the set of flags `--strict` enables for the installed mypy version (the mypy documentation says the exact list can change between versions; `warn_unreachable` is not part of it and is enabled separately in the skeleton).

### MADR 4.0.0 minimal ADR
The headings below come from the MADR 4.0.0 development template (MADR project documentation). VERIFY: compare against the 4.0.0 "minimal" template in the MADR repository and adopt it if the team prefers fewer sections.

```markdown
---
status: proposed   # proposed | accepted | rejected | deprecated | superseded by 0007
date: 2026-11-25
decision-makers: <group or role>
---

# <Short title that names problem and chosen solution>

## Context and Problem Statement

<Why a decision is needed.>

## Considered Options

- <Option 1>
- <Option 2>

## Decision Outcome

Chosen option: "<Option 1>", because <justification>.

### Consequences

- Good, because <positive consequence>
- Bad, because <negative consequence>
```

### Commit message examples
```
feat(api): add claim status endpoint
fix(adapters)!: return problem details on upstream timeout

BREAKING CHANGE: clients must handle application/problem+json on 504.
docs(adr): record choice of OpenTelemetry Collector
```

### Commit subject check: `scripts/check_commit_msg.py`
Tested on 2026-11-25 against a scratch repository with five commits (accepts valid subjects; rejects `Fixed stuff`, `feat:no space` and a `fixup!` subject). In GitLab CI run it as `python scripts/check_commit_msg.py "$CI_MERGE_REQUEST_DIFF_BASE_SHA..HEAD"`. VERIFY: that predefined variable's name and availability for your pipeline type against docs.gitlab.com; it was not executed in GitLab.

```python
#!/usr/bin/env python3
"""Check that commit subjects follow Conventional Commits 1.0.0.

Usage: scripts/check_commit_msg.py <git-rev-range>   e.g. origin/main..HEAD
Reads subjects with `git log --format=%s`. Merge commits and fixup commits are rejected.
"""

import re
import subprocess
import sys

TYPES = ("feat", "fix", "docs", "refactor", "test", "chore", "build", "ci", "perf", "revert")
SUBJECT = re.compile(rf"^({'|'.join(TYPES)})(\([a-z0-9][a-z0-9._/-]*\))?!?: \S.{{0,70}}$")


def main(rev_range: str) -> int:
    out = subprocess.run(  # noqa: S603
        ["git", "log", "--format=%s", rev_range],  # noqa: S607
        check=True, capture_output=True, text=True,
    ).stdout
    bad = [s for s in out.splitlines() if not SUBJECT.match(s)]
    for subject in bad:
        print(f"Not a Conventional Commit subject: {subject!r}")
    return 1 if bad else 0


if __name__ == "__main__":
    if len(sys.argv) != 2:
        sys.exit(__doc__)
    sys.exit(main(sys.argv[1]))
```

The type list beyond `feat` and `fix` is an org convention: the specification itself only defines `feat`, `fix`, the `!` marker and the `BREAKING CHANGE` footer, and allows other types.

### CODEOWNERS
GitLab looks for the file in `./CODEOWNERS`, `./docs/CODEOWNERS` or `./.gitlab/CODEOWNERS` and uses the first it finds; use the root. Syntax summary from docs.gitlab.com: `#` comment lines only (no inline comments), paths starting with `/` anchor at the repo root, `[Section]` headers, `^[Section]` optional sections, owners as `@group` or `@group/subgroup`, and the last matching entry in a section wins. VERIFY: the example below follows that documentation but was not run against a GitLab instance. Group names are placeholders.

```
# Default owner for everything
* @example-org/platform-team

[Infrastructure]
/infra/ @example-org/platform-team @example-org/security-team
/.gitlab-ci.yml @example-org/platform-team @example-org/security-team

[Agent configuration][2]
/.claude/ @example-org/platform-team @example-org/security-team
/.mcp.json @example-org/platform-team @example-org/security-team
/CLAUDE.md @example-org/platform-team
/AGENTS.md @example-org/platform-team

[AI registry and prompts]
/registry/ @example-org/ai-governance @example-org/platform-team
/prompts/ @example-org/ai-governance @example-org/platform-team
/evals/**/thresholds.yaml @example-org/ai-governance

[Architecture decisions]
/docs/adr/ @example-org/architecture-guild

[Ownership itself]
/CODEOWNERS @example-org/platform-team @example-org/security-team
```

Notes:
- The `[Section][2]` form requires two approvals and applies on protected branches only, per the GitLab documentation.
- Code owner approval only applies to merge requests whose target branch is protected with "Required approval from code owners"; users allowed to push directly can bypass merge request checks, so restrict direct push on the default branch.
- Files that match no entry (new paths, renames) need no code owner approval, which is why the `*` default exists.

## Checklist
- [ ] Layout matches the reference tree; no extra top-level directories without an ADR.
- [ ] `src/<package>/` follows the canonical tree; import-linter contracts exist and pass in `make check`.
- [ ] `domain/` has no outward, framework, I/O or LLM imports.
- [ ] All I/O is in `adapters/`; tools call use cases; agents never import `api/`.
- [ ] `config.py` is the only environment reader; `main.py` is the only wiring point.
- [ ] `make fmt-check` and `mypy --strict` pass; no bare `# type: ignore`.
- [ ] Every ADR uses the MADR headings and is numbered; superseded ADRs are linked.
- [ ] Commit subjects and the MR title are Conventional Commits; breaking changes use `!` and a footer.
- [ ] `CODEOWNERS` exists, uses groups, covers `infra/`, `.claude/`, `.mcp.json`, `registry/`, `prompts/`, `.gitlab-ci.yml`.
- [ ] Default branch is protected with code owner approval (or a documented fallback).

## Common AI failure modes
| Failure | What to do instead |
|---|---|
| Puts everything in one flat package or a `utils.py` | Place code in the layer that owns it; keep `common/` tiny |
| Calls the database or LLM SDK from a router or from `domain/` | Use a use case in `application/` and an adapter behind a port |
| Lets `ai/tools` import `adapters/` "just this once" | Call the use case; add it if missing |
| Reads `os.environ` in random modules | `config.py` only |
| Writes commit messages like "update stuff" or "Fix bug" | `fix(scope): imperative description` |
| Uses `fixup!` or merge commits in the MR | Clean history before review; squash through the MR title |
| Creates a flat `docs/` full of unnumbered notes | ADRs in `docs/adr/NNNN-title.md`, runbooks in `docs/runbooks/` |
| Puts `CODEOWNERS` under a GitHub-specific directory | GitLab uses `CODEOWNERS` at the root (or `docs/`, `.gitlab/`) |
| Lists individual usernames as owners | Use groups |
| Adds a type like `feature:` or `bugfix:` | Use `feat` and `fix` |
| Edits `CODEOWNERS` to remove a reviewer so the MR can merge | Never; ask the owning group |
